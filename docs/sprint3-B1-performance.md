# Sprint 3 B1 核心接口性能优化记录

## 1. 验证范围

本次检查选择两个高频读场景：

- 投放记录列表：按广告主、广告类型和日期组合筛选，并按日期、ID 倒序分页。
- 投放趋势报表：按日期范围聚合投放指标，在没有广告类型条件时不需要读取广告类型表。

列表接口已经在数据库层使用 `LIMIT` 和 `OFFSET`，没有发现 N+1 查询或先查全量再内存分页的问题。本次不引入缓存，只处理执行计划能够证明的索引和 JOIN 问题。

## 2. 测试环境与方法

- 数据库：PostgreSQL 16 Alpine 独立容器。
- 数据量：10 个广告主、4 种广告类型、500,000 条投放记录。
- 比较方法：同一容器、同一批数据、相同查询参数，分别执行 `EXPLAIN (ANALYZE, BUFFERS)`。
- 可复现脚本：`scripts/sprint3-core-performance.sql`。
- 安全措施：脚本只允许在隔离库 `advertiser_crm_perf` 上运行，所有造数和临时索引操作均在事务中执行并最终回滚。

## 3. 优化结果

### 3.1 投放记录组合筛选与分页

查询条件为一个广告主、一种广告类型和两年日期范围，返回前 20 条记录。

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 执行时间 | 0.418 ms | 0.191 ms | 降低 54.3% |
| 执行阶段共享缓冲页 | 464 | 27 | 降低 94.2% |
| 被额外过滤的记录 | 425 | 0 | 不再扫描其他广告主记录 |

优化前使用 `idx_advertising_delivery_type_date`，数据库先按广告类型和日期读取，再过滤广告主。新增以下索引后，筛选列和稳定排序列都能直接进入索引条件：

```sql
CREATE INDEX idx_delivery_advertiser_type_date_id
    ON advertising_delivery_records (
        advertiser_id,
        advertising_type_id,
        record_date DESC,
        id DESC
    );
```

优化后的执行计划使用 `idx_delivery_advertiser_type_date_id`，不再出现额外的广告主过滤和增量排序。

### 3.2 投放趋势聚合

查询条件为 2026-07-01 至 2026-07-31，共聚合 21,080 条记录。

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 执行时间 | 14.881 ms | 12.061 ms | 降低 19.0% |
| 执行阶段共享缓冲页 | 4,283 | 4,282 | 少读取广告类型表 1 页 |
| 计划节点 | Hash Join + Bitmap Heap Scan | Bitmap Heap Scan | 移除无用 JOIN |

报表 SQL 现在只在请求包含 `advertisingTypeCode` 时关联 `advertising_types`。存在该筛选条件时查询行为不变；没有该条件时避免无意义的表扫描和 Hash Join。
