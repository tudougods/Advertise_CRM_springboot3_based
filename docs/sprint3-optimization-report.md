# Advertiser CRM 后端系统总结与优化报告

> 项目：Advertiser CRM Backend
> 技术基线：Java 21、Spring Boot 3.5、PostgreSQL 16、MyBatis-Plus、Flyway
> 总结范围：Sprint 1 至 Sprint 3

## 1. 报告说明

Advertiser CRM 是面向广告业务后台的模块化单体服务。系统围绕“内部人员管理广告主、记录广告投放、查看统计结果、管理广告主资金并处理充值”这一业务闭环展开。本报告以当前代码、数据库迁移和自动化测试为依据，总结系统设计、关键实现与 Sprint 3 工程化优化结果。

系统当前是可独立运行和验证的后端项目，不包含前端页面，也没有接入真实支付渠道。支付模块通过带签名的模拟回调验证订单状态、资金入账和幂等处理方式；仅供本地使用的主动模拟接口由 Spring Profile 隔离。

## 2. 业务目标与角色

### 2.1 业务目标

项目解决以下后台管理问题：

1. 统一管理内部用户、账号状态和操作权限。
2. 维护广告主档案、分类和负责人关系。
3. 记录可追踪、可修正的广告投放事实数据。
4. 按时间、广告主和广告类型统计展示、点击、转化与花费。
5. 管理广告主账户余额，并为每次资金变化保留不可变流水。
6. 通过充值订单和支付回调完成可审计、可幂等的充值入账。

### 2.2 系统角色

| 角色 | 主要职责 | 权限边界 |
| --- | --- | --- |
| `ADMIN` | 用户管理、广告主维护、投放修正、消费扣款、充值订单创建和本地支付模拟 | 可以执行系统管理和资金写操作 |
| `OPERATOR` | 查询广告主、投放记录、统计报表、账户和资金流水，录入投放数据 | 不能维护用户、执行消费扣款或修改关键业务状态 |

公开注册只创建 `PENDING OPERATOR`，账号必须由管理员激活后才能登录。系统同时保护最后一个 `ACTIVE ADMIN`，避免管理员被并发降级、禁用或删除后失去系统管理入口。

## 3. 核心业务对象与关系

| 业务对象 | 职责 | 关键关系 |
| --- | --- | --- |
| 用户 | 保存内部账号、BCrypt 密码摘要、角色和状态 | 一个用户可以负责多个广告主，也可以成为资金流水操作人 |
| 广告主分类 | 表示广告主所属行业或业务分类 | 一个分类可以关联多个广告主；删除分类时广告主保留 |
| 广告主 | 保存企业档案、负责人、分类和启停状态 | 拥有多条投放记录，并且必须且只能拥有一个资金账户 |
| 广告类型 | 表示 `SEARCH`、`DISPLAY`、`VIDEO`、`SOCIAL` 等投放形式 | 一个类型可以关联多条投放记录 |
| 投放记录 | 保存外部编号、业务日期、漏斗指标和花费 | 归属于一个广告主和一个广告类型；消费流水可以引用它 |
| 广告主账户 | 保存当前可用余额 | 与广告主一对一，拥有多条资金流水和充值订单 |
| 资金流水 | 保存每次充值或消费及变更后余额 | 只追加，不提供修改或删除接口；可引用投放记录或充值订单 |
| 充值订单 | 保存充值金额、订单状态和支付结果 | 归属于一个账户，可以接收多次回调，但最多生成一条充值流水 |
| 支付回调审计 | 保存事件号、载荷摘要和处理结果 | 归属于充值订单，通过事件号和载荷摘要支持幂等与冲突识别 |

系统以广告主作为主要业务聚合入口：广告主连接投放事实和资金账户，投放事实进入报表聚合，资金账户连接消费流水和充值订单。业务编号承担跨请求追踪和幂等职责，数据库自增 ID 只用于内部关联。

## 4. 主要业务流程

### 4.1 用户注册与授权

1. 用户匿名提交注册申请，系统固定创建 `PENDING OPERATOR`。
2. 管理员审核并将账号改为 `ACTIVE`。
3. 用户使用用户名和密码登录，认证成功后获得 Bearer JWT。
4. Spring Security 根据 Token、角色和数据库中的实时账号状态决定是否允许访问。
5. 登录和注册入口按客户端与用户名维度限流，降低暴力尝试和批量注册风险。

### 4.2 广告主建档与投放记录

1. 管理员创建分类和广告主，可为广告主指定启用的分类与负责人。
2. 创建广告主时，系统在同一事务内建立零余额账户。
3. 管理员或运营人员录入投放记录，外部记录号用于防止重复导入。
4. 展示量、点击量、转化量和花费先经过参数校验，PostgreSQL 约束继续作为最后保护。
5. 投放记录支持组合筛选和数据库物理分页；已关联资金流水的记录不能随意删除或换绑广告主。

### 4.3 投放统计报表

1. 调用方提供日期范围，并可按广告主或广告类型筛选。
2. Service 统一处理默认日期、最大跨度、时间粒度和排序白名单。
3. Mapper 在 PostgreSQL 中完成总览、日/周/月趋势、广告主维度和广告类型维度聚合。
4. 比率指标使用聚合后的总量重新计算，零分母返回稳定的零值。
5. 响应统一控制金额和比率精度，分页报表同时返回总数和分页元数据。

### 4.4 广告消费扣款

1. 管理员提交广告主、消费金额、唯一业务号以及可选投放记录。
2. 系统校验广告主账户、投放归属和业务号。
3. 数据库使用带 `balance >= amount` 条件的原子更新扣减余额。
4. 扣款成功后，在同一事务中追加 `CONSUMPTION` 流水并记录变更后余额。
5. 余额不足、重复业务号或关联冲突会使整个事务失败，不会出现只扣余额或只写流水的中间状态。

### 4.5 充值订单与支付回调

1. 管理员为广告主账户创建 `PENDING` 充值订单。
2. 本地环境可以主动模拟成功或失败；默认及生产 Profile 不注册该入口。
3. 对外回调入口先校验时间戳、请求体大小和 HMAC-SHA256 签名，再解析业务载荷。
4. 回调服务按事件号建立审计记录，并锁定充值订单处理状态迁移。
5. 成功回调在同一事务内更新订单、增加账户余额并追加唯一 `RECHARGE` 流水。
6. 重复事件返回幂等结果；相同事件号携带不同载荷、金额不符或广告主不符时记录拒绝原因并返回明确冲突。

## 5. 系统架构

### 5.1 架构形式

项目采用模块化单体。一个 Spring Boot 应用负责 HTTP API、认证授权、业务事务和数据访问，一个 PostgreSQL 实例保存业务数据。当前规模下，这种形式能保持部署和事务简单，同时通过业务模块边界避免所有代码堆积在全局 Controller、Service 和 Mapper 目录中。

```text
客户端
  │ HTTP / JSON / Bearer JWT
  ▼
Spring Security + Request ID Filter
  ▼
Controller：路由、权限、参数校验、统一响应
  ▼
Service：业务规则、状态机、事务边界
  ▼
Mapper / MyBatis XML：持久化、物理分页、聚合 SQL
  ▼
PostgreSQL：外键、唯一约束、检查约束、触发器、行锁
```

### 5.2 模块划分

| 模块 | 主要职责 |
| --- | --- |
| `auth` | 注册登录、JWT、认证限流和 Spring Security 接入 |
| `user` | 用户、角色和账号状态管理 |
| `advertiser` | 广告主、分类和负责人关系 |
| `delivery` | 广告类型和投放记录 |
| `report` | 投放指标、趋势和维度报表 |
| `account` | 账户余额、消费和资金流水 |
| `payment` | 充值订单、状态机、模拟支付和回调审计 |
| `common` | 统一响应、分页、异常契约和 Request ID |
| `config` | Security、MyBatis、OpenAPI、时间等应用级配置 |

业务模块内部按实际需要划分 `controller`、`service`、`mapper`、`entity`、`dto`、`exception`、`model` 和 `validation`。Controller 不直接访问 Mapper，Service 不拼装 HTTP 响应，数据库负责不可绕过的数据完整性约束。

### 5.3 数据与事务边界

Flyway 负责从 V1 到 V11 的数据库演进，历史迁移不回写，新结构通过更高版本迁移追加。应用校验用于尽早反馈，数据库约束用于抵御并发请求、代码遗漏和绕过应用的非法写入。

关键事务包括：

- 创建广告主与创建零余额账户。
- 原子扣减余额与追加消费流水。
- 支付成功后的订单更新、余额增加、充值流水和回调审计。
- 管理员状态变更时对启用管理员集合加锁。

业务历史采用限制删除或解除引用的方式保护。投放、流水或充值历史存在时，广告主不能被物理删除；资金流水本身没有修改和删除接口。

## 6. Sprint 迭代过程

### 6.1 Sprint 1：建立管理基础

Sprint 1 完成公共 Web 规范、PostgreSQL/Flyway 基线、用户认证与权限、用户管理、广告主分类和广告主档案。此阶段建立了模块化分包、统一响应、JWT、角色控制和数据库约束，为后续业务模块提供稳定入口。

### 6.2 Sprint 2：形成业务闭环

Sprint 2 增加投放数据、统计报表、广告主账户、消费流水、充值订单和模拟支付回调。开发重点从普通 CRUD 扩展到聚合 SQL、资金一致性、并发控制、状态机、HMAC 验签和幂等处理，并通过 V3 至 V10 逐步补强数据库约束。

### 6.3 Sprint 3：工程化收尾

Sprint 3 不增加业务模块，围绕现有系统完成统一响应与错误码审核、参数校验、全局异常处理、核心 SQL 性能优化、日志分级、重复逻辑整理、项目结构说明和运行文档。数据库增加 V11 组合索引，报表查询按条件移除无用 JOIN；最终通过自动化回归和容器运行验证确认优化没有改变业务行为。

## 7. 核心技术难点与解决方案

### 7.1 认证、权限与账号状态

#### 问题

只验证 JWT 签名并不能保证当前请求仍然有效。用户可能在 Token 有效期内被禁用或保持待审批状态；管理员变更还必须保证系统始终保留至少一个可用管理员。公开登录和注册端点同时面临重复尝试风险。

#### 方案

- 密码只保存 BCrypt 摘要，登录失败统一返回凭据错误，避免泄露用户名是否存在。
- JWT 使用 Base64 编码的至少 32 字节 HMAC 密钥，并通过 Bearer Token 传递。
- 每次认证请求解析 Token 后重新读取用户，只有数据库状态为 `ACTIVE` 才建立 SecurityContext；角色也以数据库当前值为准。
- Controller 使用 Spring Security 声明 ADMIN/OPERATOR 权限，401 和 403 使用统一 JSON 响应。
- 公开注册固定创建 `PENDING OPERATOR`，不允许客户端自行创建管理员。
- 降级、禁用或删除管理员前，数据库锁定启用管理员集合；Service 和数据库触发器共同保护最后一个 `ACTIVE ADMIN`。
- 登录按“客户端 IP + 用户名”限流，注册按客户端 IP 限流；成功登录清除对应失败计数。

#### 验证

- Web 测试覆盖匿名访问、无效 Token、待审批/禁用账号、ADMIN/OPERATOR 权限和统一 401/403 响应。
- [管理员约束测试](../src/test/java/com/internship/crm/user/service/UserAdminInvariantPersistenceTest.java)验证最后一个管理员不能被删除或禁用。
- [管理员并发锁测试](../src/test/java/com/internship/crm/user/service/UserAdminLockPersistenceTest.java)验证并发状态变更会被串行化。
- [认证限流测试](../src/test/java/com/internship/crm/auth/service/AuthRateLimiterTest.java)验证窗口到期、不同维度隔离和超限行为。

### 7.2 统计口径与动态聚合查询

#### 问题

展示量、点击量、转化量和花费不能按单行比率再取平均，必须先汇总分子分母后重新计算。查询同时支持可选日期、广告主、广告类型、时间粒度、排序和分页，若直接拼接参数会产生口径不一致和 SQL 注入风险。

#### 方案

- 未提供日期时使用业务时区内包含当天的最近 30 天；显式日期必须成对提供、顺序正确且跨度不超过 366 天。
- 时间粒度、排序字段和排序方向使用枚举白名单，再映射为受控 SQL 片段。
- 总览、趋势和多维统计均在 PostgreSQL 聚合；CTR、CVR、CPC 使用汇总结果计算，并通过 `NULLIF` 与 `COALESCE` 处理零分母。
- 广告主报表的数据查询和 COUNT 复用同一组过滤条件，保证分页总数一致。
- 只有存在广告类型筛选时才 JOIN `advertising_types`，避免无条件读取无用字典表。
- 趋势按自然日、以周一为起点的自然周或自然月聚合，并使用稳定排序。

#### 验证

- [查询条件测试](../src/test/java/com/internship/crm/report/service/DeliveryReportQueryNormalizerTest.java)覆盖默认范围、业务时区、空白类型、倒序和超大日期范围。
- [聚合 SQL 测试](../src/test/java/com/internship/crm/report/mapper/DeliveryReportMapperTest.java)使用固定数据核对总量、比率、筛选和零分母结果。
- [趋势测试](../src/test/java/com/internship/crm/report/mapper/DeliveryReportTrendMapperTest.java)验证日、周、月边界。
- [维度报表测试](../src/test/java/com/internship/crm/report/mapper/DeliveryReportDimensionMapperTest.java)验证排序白名单、分页总数和广告类型汇总。

### 7.3 账户余额、不可变流水与并发扣款

#### 问题

“先查询余额、再扣款”在并发请求下会产生超扣；余额和流水若分开提交，会出现账实不一致。重复请求还可能使用同一业务号扣款多次，投放记录换绑也可能破坏流水归属。

#### 方案

- 广告主与账户保持一对一，余额使用 `NUMERIC(19,2)` 且数据库禁止负数。
- 消费 SQL 通过 `UPDATE ... WHERE balance >= amount RETURNING balance` 原子判断并扣款。
- 余额更新和 `CONSUMPTION` 流水插入位于同一事务；后续校验或写流水失败时自动回滚扣款。
- `business_no` 全局唯一，写入使用条件插入处理并发重复请求。
- 流水保存正金额、方向和 `balance_after`，不提供修改或删除接口。
- 消费关联投放记录时锁定该记录并校验广告主归属；数据库触发器继续防止绕过 Service 的跨广告主关联和结算后换绑。

#### 验证

- [账户事务测试](../src/test/java/com/internship/crm/account/service/AdvertiserAccountConsumptionPersistenceTest.java)覆盖余额不足、事务回滚、相同业务号竞争、两个消费竞争同一余额和账实一致性。
- [账户业务规则测试](../src/test/java/com/internship/crm/account/service/AdvertiserAccountConsumptionServiceTest.java)覆盖金额精度、投放归属、重复业务号和并发冲突转换。
- 数据库迁移测试验证余额非负、业务号唯一、流水引用类型以及跨广告主一致性约束。

### 7.4 支付回调验签、状态机与幂等

#### 问题

支付回调是公开入口，不能依赖用户 JWT。系统必须确认请求来自持有共享密钥的调用方，拒绝重放和篡改，并处理相同事件的重复或并发到达。订单、余额、流水和回调审计还必须保持一致。

#### 方案

- 使用 `HMAC-SHA256(secret, timestamp + "." + rawBody)` 验签，比较时采用常量时间算法。
- 验签发生在 JSON 解析前；请求体限制为 16 KiB，时间戳必须位于配置的容忍窗口内。
- 密钥必须是 Base64 编码且解码后至少 32 字节；服务端只保存回调载荷 SHA-256 摘要，不保存共享密钥或原始签名。
- JSON 拒绝未知字段和尾随内容，验签后继续校验订单号、事件号、广告主、金额、结果与平台交易号。
- 订单只允许 `PENDING -> SUCCESS/FAILED/CLOSED`，终态不能回退。
- `provider_event_id`、`business_no`、`recharge_order_id` 和平台交易号上的唯一约束形成多层幂等保护。
- 处理成功时，在同一事务内更新订单、增加余额、写入充值流水并完成回调审计。
- 已处理的相同事件和相同载荷返回幂等确认；相同事件号但不同摘要返回冲突。可信但业务不一致的回调使用独立事务保留 `REJECTED` 审计。

#### 验证

- [HMAC 验签测试](../src/test/java/com/internship/crm/payment/service/PaymentCallbackSignatureServiceTest.java)覆盖格式、密钥强度、请求体大小、时间窗口和原始字节签名。
- [回调事务测试](../src/test/java/com/internship/crm/payment/service/MockPaymentCallbackPersistenceTest.java)覆盖合法成功/失败、事件并发、重复事件、载荷冲突、业务字段篡改和事务回滚。
- 回调 Web 测试确认端点无需 JWT，但所有成功和失败仍使用统一 API 错误契约。
- Profile 隔离测试确认生产环境不注册主动模拟支付 Controller、Service 和平台交易号生成器。

## 8. Sprint 3 工程化优化

### 8.1 统一响应、错误码与异常处理

- 所有业务 Controller 返回 `ApiResponse<T>` 或 `ResponseEntity<ApiResponse<T>>`；分页数据使用 `PageResponse<T>`。
- 响应固定包含 `success`、`code`、`message`、`data`、`timestamp` 和 `requestId`。
- 公共错误码使用 `COMMON_`，业务错误码使用所属模块前缀；自动化测试检查全局唯一性、命名格式和精确 HTTP 状态映射。
- 全局异常处理覆盖参数绑定、Bean Validation、类型转换、非法 JSON、方法不支持、媒体类型、资源不存在、数据库冲突和未知异常。
- 401/403 由 Spring Security 入口保持相同响应结构；未知异常只向客户端返回安全的 `COMMON_INTERNAL_ERROR`。

### 8.2 参数校验

- DTO 校验必填、长度、格式、数值范围和金额精度，Controller 校验路径 ID、分页上限、日期粒度和排序枚举。
- 投放漏斗关系在字段同时提供时由 Bean Validation 提前拒绝；局部更新只提供部分指标时，由 Service 合并旧值后再次校验。
- Service 保留金额、业务编号、状态迁移和跨实体关系等防御性校验，数据库约束继续作为最后保护。
- 校验错误统一返回字段或对象级规则名称，非法输入在核心业务写入前被拒绝。

### 8.3 核心接口性能

Sprint 3 使用 PostgreSQL 16 和 500,000 条固定投放记录复现优化前后执行计划，详细结果见 [B1 性能优化记录](sprint3-B1-performance.md)：

| 场景 | 优化前 | 优化后 | 结果 |
| --- | ---: | ---: | --- |
| 投放组合筛选分页 | 0.418 ms，464 个共享缓冲页 | 0.191 ms，27 个共享缓冲页 | 时间降低 54.3%，缓冲页降低 94.2% |
| 31 天趋势聚合 | 14.881 ms，Hash Join | 12.061 ms，无无用 JOIN | 时间降低 19.0% |

V11 新增 `(advertiser_id, advertising_type_id, record_date DESC, id DESC)` 组合索引，使常用组合筛选与稳定排序直接匹配索引。报表 SQL 在没有类型条件时不再 JOIN 类型表。优化没有引入缓存，也没有改变接口结果或业务规则；复现脚本位于 [`scripts/sprint3-core-performance.sql`](../scripts/sprint3-core-performance.sql)。

### 8.4 日志、安全与可维护性

- Request ID 过滤器为每个请求生成或接收经过字符和长度限制的追踪 ID，并记录方法、路径、状态和耗时。
- `ERROR` 用于未知异常和 5xx 故障，`WARN` 用于权限拒绝、冲突和限流，`INFO` 用于请求完成与关键业务状态，普通可预期参数错误使用 `DEBUG`。
- 请求日志不记录请求体、查询参数、Authorization、密码、JWT、密钥、签名或原始支付载荷；日志检查见 [B2 日志分级记录](sprint3-B2-logging.md)。
- 支付订单号和平台交易号的格式、长度与规范化逻辑集中到 `PaymentReferenceRules`，消除 Controller 与多个 Service 的重复规则。
- 项目保持按业务模块分包，复杂报表 SQL 放在 MyBatis XML，事务边界集中在 Service，模块放置规则见 [项目结构说明](project-structure.md)。

## 11. 当前限制

1. **认证限流只适用于单实例。** 当前使用进程内固定窗口，并直接读取连接地址；多实例部署时计数不会共享，经过反向代理时也需要可信地解析真实客户端地址。
2. **JWT 生命周期较简单。** 系统没有 Refresh Token、单 Token 撤销列表或密钥版本轮换；禁用账号可立即阻止继续访问，但无法只撤销某一个已签发 Token。
3. **支付能力是模拟实现。** 当前没有真实支付渠道 SDK、退款、对账、主动查单和支付渠道故障补偿，不能直接承担真实资金业务。
4. **报表直接查询业务库。** 当前数据规模下 PostgreSQL 聚合足够；更大规模、长周期或高并发报表可能需要分区、预聚合或独立分析存储。
5. **投放数据以同步 API 录入。** 尚未实现批量文件导入、消息队列、失败重试和数据质量任务，不适合直接承接大规模渠道数据流。
6. **审计范围有限。** 资金流水和支付回调具有审计记录，但用户、广告主和分类等管理操作没有完整的操作前后快照；无业务历史的数据仍采用物理删除。
7. **部署配置以本地和验收为主。** Compose 验证了可运行性，但没有包含 TLS、外部密钥管理、数据库备份、高可用、指标告警和自动化 CI/CD。
8. **项目只交付后端。** 当前没有前端界面、通知中心或审批工作台，功能主要通过 API 和 Swagger 使用。

这些限制不影响当前实习项目范围内的功能和验收，但必须在进入共享环境、生产环境或更大数据规模前处理。

## 12. 未来扩展方向

### 12.1 认证与平台安全

- 将认证限流迁移到 Redis 等共享存储，并在可信反向代理边界统一客户端地址。
- 引入 Refresh Token 轮换、Token ID 撤销和签名密钥版本管理。
- 增加管理操作审计表，记录操作人、对象、变更前后摘要和 Request ID。
- 对登录、权限拒绝、支付回调失败等风险事件建立指标和告警。

### 12.2 支付与资金能力

- 在现有 `payment` 接口和状态机后增加支付渠道适配器，保持订单与账户模块不依赖具体 SDK。
- 增加主动查单、退款、日终对账和差错处理，所有外部动作继续使用业务号和幂等键。
- 对需要跨系统可靠投递的事件采用 Outbox，再由异步任务发送，避免数据库事务与消息发送出现双写不一致。

### 12.3 投放数据与报表

- 增加批量导入任务、文件校验、错误行报告和可重试的数据接入流程。
- 数据量增长后按业务日期分区，并根据实际慢查询决定是否增加预聚合表或物化视图。
- 当分析负载明显影响交易库时，再通过变更数据捕获或批处理同步到独立分析存储。
- 扩展渠道、计划、活动等维度时，继续保持事实表与字典/维度表职责清晰。

### 12.4 工程与交付

- 建立 CI 流水线，自动执行编译、420 项回归、迁移测试、镜像构建和依赖安全检查。
- 为共享环境增加 TLS、外部 Secret、数据库备份恢复演练和最小权限数据库账号。
- 接入结构化日志、指标和链路追踪，以 Request ID 关联接口、SQL 和外部调用。
- 继续保持模块化单体；只有当团队、部署频率或负载边界明确分离时，再评估拆分报表、数据接入或支付适配模块。

## 13. 总结

Advertiser CRM 已形成从内部用户、广告主档案、投放记录、统计报表到账户消费和模拟充值的完整后端业务链路。项目的主要价值不在接口数量，而在于把权限、状态、资金和回调等容易出错的规则落实到 Service 事务、原子 SQL、唯一约束、触发器和自动化测试中。

Sprint 3 完成了工程化收尾：统一响应与错误语义，补强输入校验和异常兜底，依据执行计划优化核心查询，建立可追踪且不泄露敏感信息的日志体系，并补齐项目结构、运行方式和复现材料。合并后的系统通过 420 项自动化测试以及完整容器启动验证，当前实现满足本次实习任务的后端交付范围。
