# Advertiser CRM 后端系统总结与优化报告

> 项目：Advertiser CRM Backend  
> 技术基线：Java 21、Spring Boot 3.5、PostgreSQL 16、MyBatis-Plus、Flyway  
> 总结范围：Sprint 1 至 Sprint 3

## 1. 报告说明

Advertiser CRM 是面向广告业务后台的模块化单体服务。系统围绕“内部人员管理广告主、记录广告投放、查看统计结果、管理广告主资金并处理充值”这一业务闭环展开。本报告以当前代码、数据库迁移和自动化测试为依据，总结系统设计、关键实现与 Sprint 3 工程化优化结果。

系统当前是可独立运行和验证的后端项目，不包含前端页面，也没有接入真实支付渠道。支付模块通过带签名的模拟回调验证订单状态、资金入账和幂等处理方式；仅供本地使用的主动模拟接口由 Spring Profile 隔离。

## 2. 业务目标与角色

### 2.1 业务目标

项目解决以下后台管理问题：

1. 统一管理内部用户、账号状态和操作权限。
2. 维护广告主档案、分类和负责人关系。
3. 记录可追踪、可修正的广告投放事实数据。
4. 按时间、广告主和广告类型统计展示、点击、转化与花费。
5. 管理广告主账户余额，并为每次资金变化保留不可变流水。
6. 通过充值订单和支付回调完成可审计、可幂等的充值入账。

### 2.2 系统角色

| 角色 | 主要职责 | 权限边界 |
| --- | --- | --- |
| `ADMIN` | 用户管理、广告主维护、投放修正、消费扣款、充值订单创建和本地支付模拟 | 可以执行系统管理和资金写操作 |
| `OPERATOR` | 查询广告主、投放记录、统计报表、账户和资金流水，录入投放数据 | 不能维护用户、执行消费扣款或修改关键业务状态 |

公开注册只创建 `PENDING OPERATOR`，账号必须由管理员激活后才能登录。系统同时保护最后一个 `ACTIVE ADMIN`，避免管理员被并发降级、禁用或删除后失去系统管理入口。

## 3. 核心业务对象与关系

| 业务对象 | 职责 | 关键关系 |
| --- | --- | --- |
| 用户 | 保存内部账号、BCrypt 密码摘要、角色和状态 | 一个用户可以负责多个广告主，也可以成为资金流水操作人 |
| 广告主分类 | 表示广告主所属行业或业务分类 | 一个分类可以关联多个广告主；删除分类时广告主保留 |
| 广告主 | 保存企业档案、负责人、分类和启停状态 | 拥有多条投放记录，并且必须且只能拥有一个资金账户 |
| 广告类型 | 表示 `SEARCH`、`DISPLAY`、`VIDEO`、`SOCIAL` 等投放形式 | 一个类型可以关联多条投放记录 |
| 投放记录 | 保存外部编号、业务日期、漏斗指标和花费 | 归属于一个广告主和一个广告类型；消费流水可以引用它 |
| 广告主账户 | 保存当前可用余额 | 与广告主一对一，拥有多条资金流水和充值订单 |
| 资金流水 | 保存每次充值或消费及变更后余额 | 只追加，不提供修改或删除接口；可引用投放记录或充值订单 |
| 充值订单 | 保存充值金额、订单状态和支付结果 | 归属于一个账户，可以接收多次回调，但最多生成一条充值流水 |
| 支付回调审计 | 保存事件号、载荷摘要和处理结果 | 归属于充值订单，通过事件号和载荷摘要支持幂等与冲突识别 |

系统以广告主作为主要业务聚合入口：广告主连接投放事实和资金账户，投放事实进入报表聚合，资金账户连接消费流水和充值订单。业务编号承担跨请求追踪和幂等职责，数据库自增 ID 只用于内部关联。

## 4. 主要业务流程

### 4.1 用户注册与授权

1. 用户匿名提交注册申请，系统固定创建 `PENDING OPERATOR`。
2. 管理员审核并将账号改为 `ACTIVE`。
3. 用户使用用户名和密码登录，认证成功后获得 Bearer JWT。
4. Spring Security 根据 Token、角色和数据库中的实时账号状态决定是否允许访问。
5. 登录和注册入口按客户端与用户名维度限流，降低暴力尝试和批量注册风险。

### 4.2 广告主建档与投放记录

1. 管理员创建分类和广告主，可为广告主指定启用的分类与负责人。
2. 创建广告主时，系统在同一事务内建立零余额账户。
3. 管理员或运营人员录入投放记录，外部记录号用于防止重复导入。
4. 展示量、点击量、转化量和花费先经过参数校验，PostgreSQL 约束继续作为最后保护。
5. 投放记录支持组合筛选和数据库物理分页；已关联资金流水的记录不能随意删除或换绑广告主。

### 4.3 投放统计报表

1. 调用方提供日期范围，并可按广告主或广告类型筛选。
2. Service 统一处理默认日期、最大跨度、时间粒度和排序白名单。
3. Mapper 在 PostgreSQL 中完成总览、日/周/月趋势、广告主维度和广告类型维度聚合。
4. 比率指标使用聚合后的总量重新计算，零分母返回稳定的零值。
5. 响应统一控制金额和比率精度，分页报表同时返回总数和分页元数据。

### 4.4 广告消费扣款

1. 管理员提交广告主、消费金额、唯一业务号以及可选投放记录。
2. 系统校验广告主账户、投放归属和业务号。
3. 数据库使用带 `balance >= amount` 条件的原子更新扣减余额。
4. 扣款成功后，在同一事务中追加 `CONSUMPTION` 流水并记录变更后余额。
5. 余额不足、重复业务号或关联冲突会使整个事务失败，不会出现只扣余额或只写流水的中间状态。

### 4.5 充值订单与支付回调

1. 管理员为广告主账户创建 `PENDING` 充值订单。
2. 本地环境可以主动模拟成功或失败；默认及生产 Profile 不注册该入口。
3. 对外回调入口先校验时间戳、请求体大小和 HMAC-SHA256 签名，再解析业务载荷。
4. 回调服务按事件号建立审计记录，并锁定充值订单处理状态迁移。
5. 成功回调在同一事务内更新订单、增加账户余额并追加唯一 `RECHARGE` 流水。
6. 重复事件返回幂等结果；相同事件号携带不同载荷、金额不符或广告主不符时记录拒绝原因并返回明确冲突。

## 5. 系统架构

### 5.1 架构形式

项目采用模块化单体。一个 Spring Boot 应用负责 HTTP API、认证授权、业务事务和数据访问，一个 PostgreSQL 实例保存业务数据。当前规模下，这种形式能保持部署和事务简单，同时通过业务模块边界避免所有代码堆积在全局 Controller、Service 和 Mapper 目录中。

```text
客户端
  │ HTTP / JSON / Bearer JWT
  ▼
Spring Security + Request ID Filter
  ▼
Controller：路由、权限、参数校验、统一响应
  ▼
Service：业务规则、状态机、事务边界
  ▼
Mapper / MyBatis XML：持久化、物理分页、聚合 SQL
  ▼
PostgreSQL：外键、唯一约束、检查约束、触发器、行锁
```

### 5.2 模块划分

| 模块 | 主要职责 |
| --- | --- |
| `auth` | 注册登录、JWT、认证限流和 Spring Security 接入 |
| `user` | 用户、角色和账号状态管理 |
| `advertiser` | 广告主、分类和负责人关系 |
| `delivery` | 广告类型和投放记录 |
| `report` | 投放指标、趋势和维度报表 |
| `account` | 账户余额、消费和资金流水 |
| `payment` | 充值订单、状态机、模拟支付和回调审计 |
| `common` | 统一响应、分页、异常契约和 Request ID |
| `config` | Security、MyBatis、OpenAPI、时间等应用级配置 |

业务模块内部按实际需要划分 `controller`、`service`、`mapper`、`entity`、`dto`、`exception`、`model` 和 `validation`。Controller 不直接访问 Mapper，Service 不拼装 HTTP 响应，数据库负责不可绕过的数据完整性约束。

### 5.3 数据与事务边界

Flyway 负责从 V1 到 V11 的数据库演进，历史迁移不回写，新结构通过更高版本迁移追加。应用校验用于尽早反馈，数据库约束用于抵御并发请求、代码遗漏和绕过应用的非法写入。

关键事务包括：

- 创建广告主与创建零余额账户。
- 原子扣减余额与追加消费流水。
- 支付成功后的订单更新、余额增加、充值流水和回调审计。
- 管理员状态变更时对启用管理员集合加锁。

业务历史采用限制删除或解除引用的方式保护。投放、流水或充值历史存在时，广告主不能被物理删除；资金流水本身没有修改和删除接口。

## 6. Sprint 迭代过程

### 6.1 Sprint 1：建立管理基础

Sprint 1 完成公共 Web 规范、PostgreSQL/Flyway 基线、用户认证与权限、用户管理、广告主分类和广告主档案。此阶段建立了模块化分包、统一响应、JWT、角色控制和数据库约束，为后续业务模块提供稳定入口。

### 6.2 Sprint 2：形成业务闭环

Sprint 2 增加投放数据、统计报表、广告主账户、消费流水、充值订单和模拟支付回调。开发重点从普通 CRUD 扩展到聚合 SQL、资金一致性、并发控制、状态机、HMAC 验签和幂等处理，并通过 V3 至 V10 逐步补强数据库约束。

### 6.3 Sprint 3：工程化收尾

Sprint 3 不增加业务模块，围绕现有系统完成统一响应与错误码审核、参数校验、全局异常处理、核心 SQL 性能优化、日志分级、重复逻辑整理、项目结构说明和运行文档。数据库增加 V11 组合索引，报表查询按条件移除无用 JOIN；最终通过自动化回归和容器运行验证确认优化没有改变业务行为。
