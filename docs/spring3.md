# Advertiser CRM Sprint 3 开发计划

> Sprint 主题：工程化完善与项目总结
>
> 计划周期：第 4 周（最后一周），建议 5 个工作日
>
> 计划依据：当前 `main` 分支、Sprint 1/2 已交付功能，以及导师给出的第四周任务与产出要求

## 1. 当前项目 Review

### 1.1 已完成的业务基础

当前 `main` 已合并 Sprint 2，项目采用 Java 21、Spring Boot 3.5、MyBatis-Plus、PostgreSQL、Flyway 和 Spring Security，已经形成完整的后端业务闭环：

- `auth`：注册、登录、JWT 鉴权和认证接口限流。
- `user`：用户、角色和账号状态管理。
- `advertiser`：广告主分类与广告主档案管理。
- `delivery`：广告类型、投放数据录入、修改、删除和组合筛选分页。
- `report`：投放概览、趋势、广告主维度和广告类型维度报表。
- `account`：账户余额、充值/消费流水和原子扣款。
- `payment`：模拟充值订单、HMAC 回调验签、状态机和幂等入账。
- `common`：统一响应、全局异常处理、分页结构、Request ID 和请求日志。
- `config`：Spring Security、Swagger/OpenAPI、MyBatis-Plus 和业务配置。

数据库已通过 Flyway `V1`～`V10` 管理，Sprint 2 最终验收记录为 390 项自动化测试通过，并已完成 Swagger 全流程 Demo、并发一致性验证和核心 SQL 执行计划检查。

### 1.2 本 Sprint 需要解决的问题

Sprint 3 不再扩展新的业务模块，重点是对整个系统进行横向检查和收尾：

- 统一响应、错误码和 HTTP 状态虽然已经存在，但需要覆盖全部接口并检查边界行为是否一致。
- 参数校验需要从 DTO 注解扩展到路径、查询参数、跨字段规则和数据库约束，确认非法输入不会进入核心业务流程。
- 全局异常处理需要覆盖常见框架异常、业务异常和未知异常，并保证响应不泄露堆栈、SQL、密钥或内部路径。
- Sprint 2 已对核心聚合 SQL 做过执行计划验证，本周仍需从接口视角建立性能基线，排查慢查询、无界查询、重复查询和不必要的数据返回。
- 当前已有请求日志和部分关键业务日志，需要统一 `ERROR`、`WARN`、`INFO`、`DEBUG` 的使用边界，并补齐资金、支付和鉴权等关键链路日志。
- README 的模块说明、启动方式、配置项和 Demo 入口需要与 Sprint 2 最终代码重新核对。
- 最终需要形成一份可独立阅读的《后端系统总结与优化报告》，说明架构、难点、优化、亮点和未来方向。

## 2. Sprint 目标

本迭代的目标不是增加功能数量，而是让现有系统达到“规范一致、可验证、可运行、可交接”的状态。

Sprint 完成时应满足：

1. 所有 API 使用统一响应结构、模块化错误码和一致的 HTTP 状态语义。
2. 请求参数、跨字段业务规则和数据库约束形成分层校验，非法输入能够被稳定拦截。
3. 已知异常有明确映射，未知异常统一兜底，客户端响应不暴露内部实现细节。
4. 核心接口具有可复现的性能基线，已发现的高频或慢查询问题有测量证据和优化记录。
5. 日志级别和关键业务事件记录规范统一，可通过 Request ID 定位一次请求，同时不记录敏感数据。
6. 代码结构、命名、配置和文档与实际项目保持一致，其他开发者可以按文档完成部署、启动和演示。
7. 全量自动化测试、干净数据库迁移和核心业务回归全部通过。
8. 完成《后端系统总结与优化报告》，能够用于最后一周汇报和项目复盘。

- 核心接口性能基线、SQL 执行计划和针对性优化。
- 日志级别、日志字段、Request ID 关联和敏感信息检查。
- 代码结构、重复逻辑、命名、注释和配置文件整理。
- README、部署运行说明、配置说明、Swagger Demo 和故障排查说明更新。
- Flyway 空库迁移、全量测试、真实 HTTP 冒烟测试和最终回归。
- 编写《后端系统总结与优化报告》。

- 为本地环境增加简单的接口压测脚本。

## 4. 模块划分与开发任务

Sprint 3 分为 A、B、C、D 四个板块。每个板块对应明确的现有代码模块，可以分别开发、测试、Review 和验收；板块 D 最后负责将前三个技术板块整合为完整交付物。

| 板块 | 对应模块或范围 | 核心任务 | 主要产出 |
| --- | --- | --- | --- |
| A | `common`、`config` | 统一响应、参数校验、全局异常、日志与 OpenAPI 公共规范 | 公共能力优化代码、契约与异常测试 |
| B | `advertiser`、`delivery`、`report` | 广告主、投放和报表模块的规则复查与查询性能优化 | 业务模块修复、SQL/索引优化记录 |
| C | `auth`、`user`、`account`、`payment` | 认证权限、账户交易、支付回调和一致性完善 | 安全与交易模块修复、幂等和并发测试 |
| D | 全项目、`README`、`docs`、测试与部署配置 | 代码整理、全量回归、部署说明、总结与复盘 | 测试报告、README、系统总结与优化报告 |

### 4.1 板块 A：公共基础与工程规范模块

> 对应模块：`common`、`config`

#### 目标

统一所有业务模块共同依赖的 API 契约、校验、异常、日志和接口文档规范，为 B、C 板块提供一致的公共基础。

#### 主要任务

- 检查成功响应是否统一使用 `ApiResponse<T>`，分页接口是否统一使用 `PageResponse<T>`。
- 检查错误码接口、业务异常和 HTTP 状态之间的映射，保证错误码含义唯一且模块前缀清晰。
- 完善参数绑定失败、类型转换失败、非法 JSON、校验失败、资源不存在、数据冲突和未知异常的统一处理。
- 统一 `id`、`page`、`size`、日期、枚举等公共路径参数和查询参数校验。
- 检查 Request ID 的生成、透传、响应头/响应体写入和日志关联。
- 明确 `ERROR`、`WARN`、`INFO`、`DEBUG` 的使用边界，避免同一异常被重复记录。
- 检查 Spring Security、MyBatis-Plus、OpenAPI、Profile 和时区等公共配置。
- 检查 Swagger 的认证方式、统一模型和通用错误说明。
- 补充公共 Web 行为、异常转换、参数边界和敏感信息保护测试。

#### 可独立提交的小任务

板块 A 建议拆为 A1～A7。每个提交同时包含对应实现和测试，保证该提交可以独立编译、独立验证；不要先集中改完代码，再用一个单独提交补全部测试。

| 编号 | 小任务 | 主要文件范围 | 单独验收方式 | 建议 Commit |
| --- | --- | --- | --- | --- |
| A1 | 统一成功响应与分页结构 | `common/response/ApiResponse.java`、`PageResponse.java` 及其测试 | 验证成功/无数据/分页边界、时间戳和 Request ID | `refactor(common): standardize API response models` |
| A2 | 统一错误码与业务异常契约 | `ErrorCode.java`、`CommonErrorCode.java`、`BusinessException.java`、`RateLimitExceededException.java` 及其测试 | 验证错误码、HTTP 状态、消息和附加数据映射 | `refactor(common): unify error code contracts` |
| A3 | 完善参数校验与全局异常处理 | `GlobalExceptionHandler.java`、`FieldValidationError.java`、公共 MVC 测试控制器及测试 | 验证非法 JSON、字段校验、类型转换、路径/查询参数、业务冲突和未知异常 | `fix(common): complete validation exception handling` |
| A4 | 完善 Request ID 与请求日志 | `RequestIdContext.java`、`RequestLoggingFilter.java` 及其测试 | 验证 ID 生成/透传/清理、响应头、状态、耗时、日志级别和敏感参数过滤 | `refactor(logging): standardize request tracing` |
| A5 | 整理公共运行配置 | `ApplicationTimeConfig.java`、`MybatisPlusConfig.java`、配置文件及对应测试 | 验证合法/非法时区、分页上限、不同 Profile 的日志和公共配置 | `refactor(config): harden shared runtime configuration` |
| A6 | 统一 OpenAPI 公共定义 | `OpenApiConfig.java`、安全方案定义、公共响应 Schema 和 OpenAPI 测试 | 检查 Swagger 标题、JWT Bearer、公共模型及主要错误响应 | `docs(openapi): align shared API contracts` |
| A7 | 板块 A 回归与验收记录 | A1～A6 涉及的测试、`docs/sprint3-A-common-acceptance.md` | 运行公共模块专项测试和全量测试，记录发现、修改、结果及限制 | `test(sprint3): record module A acceptance` |

建议执行顺序为 A1 → A2 → A3 → A4 → A5 → A6 → A7。A1～A3 先固定响应和异常契约；A4、A5 在契约稳定后整理请求上下文及配置；A6 最后让 OpenAPI 与实际行为对齐；A7 只做总回归和验收归档。

#### 各提交的边界

- A1 只处理成功响应和分页模型，不同时修改业务 Controller。
- A2 只固定错误码与异常对象；具体异常捕获和响应转换放在 A3。
- A3 可以补充用于触发异常的测试 Controller，但不修改真实业务模块的业务规则。
- A4 只处理请求追踪和请求级日志；账户、支付等业务事件日志留给板块 C。
- A5 中 `SecurityConfig` 只检查公共放行路径和异常入口，具体 RBAC 权限调整留给板块 C。
- A6 只修正公共 OpenAPI 定义；某个业务接口的注解缺失应在对应的 B 或 C 板块提交。
- 如果某项审查后确认代码无需修改，不创建无意义的空重构提交，只把检查证据和结论写入 A7。

#### 日志级别约定

| 级别 | 使用场景 | 示例 |
| --- | --- | --- |
| `ERROR` | 未知异常、系统依赖故障、需要立即处理的请求失败 | 数据库不可用、未预期运行时异常 |
| `WARN` | 已处理但值得关注的业务风险 | 登录失败、余额不足、签名无效、状态冲突 |
| `INFO` | 请求完成摘要和关键业务状态变化 | 账号状态变化、消费成功、充值成功 |
| `DEBUG` | 本地排查所需的非敏感内部细节 | 查询条件摘要、分支判断、幂等命中 |

#### 完成标准

- 所有模块共享一致的响应、错误码、异常和参数校验规则。
- 同类错误使用一致的 HTTP 状态，不通过 200 响应承载失败结果。
- 一次请求可以通过 Request ID 关联入口日志、业务日志和错误响应。
- 未知异常统一兜底，客户端响应不包含堆栈、SQL、路径、密码、Token 或密钥。
- 公共规范具有 MockMvc 或单元测试，OpenAPI 描述与实际行为一致。

### 4.2 板块 B：广告主、投放与报表优化模块

> 对应模块：`advertiser`、`delivery`、`report`

#### 目标

围绕“广告主 → 投放数据 → 统计报表”主链路，复查业务规则、参数边界和查询实现，重点优化高频列表与聚合报表。

#### 主要任务

- 复查广告主名称、注册编号、分类、负责人和启用状态规则。
- 复查投放记录外部编号幂等、关联对象状态、指标非负和漏斗关系。
- 复查投放数据修改、删除及与资金流水之间的关联保护。
- 统一列表接口的物理分页、`size <= 100`、稳定排序和组合筛选行为。
- 统一报表开始/结束日期、最大跨度、时间粒度和排序字段校验。
- 检查总览、趋势、广告主排名和广告类型分布的统计口径，确认比率基于汇总后的分子、分母计算。
- 固定数据规模和查询样例，对列表及聚合 SQL 执行 `EXPLAIN (ANALYZE, BUFFERS)`。
- 排查 N+1、重复查询、无界查询、内存分页、无用返回列以及不合理 JOIN 或排序。
- 只在执行计划证明需要时通过新 Flyway 迁移增加索引，不修改 `V1`～`V10`。
- 为非法筛选、边界日期、分页、统计口径和优化后的 SQL 补充回归测试。

#### 核心检查对象

| 模块 | 核心接口 | 优化重点 |
| --- | --- | --- |
| `advertiser` | 广告主、分类列表与详情 | 分页、关联查询、唯一性和状态校验 |
| `delivery` | 投放记录录入与组合筛选 | 幂等、日期范围、稳定排序和组合索引 |
| `report` | 概览、趋势和维度报表 | 聚合口径、JOIN、排序和执行计划 |

#### 可独立提交的小任务

| 编号 | 小任务 | 主要文件范围 | 单独验收方式 | 建议 Commit |
| --- | --- | --- | --- | --- |
| B1 | 复查广告主与分类规则 | `advertiser` 的 Controller、DTO、Service、Mapper 及测试 | 验证唯一性、分类/负责人状态、清除关系、删除规则和分页 | `fix(advertiser): harden profile and category rules` |
| B2 | 复查投放数据规则 | `delivery` 的 Controller、DTO、Service、Mapper 及测试 | 验证外部编号幂等、指标漏斗、关联状态、修改/删除保护和筛选 | `fix(delivery): harden delivery record rules` |
| B3 | 统一报表查询与统计口径 | `report` 的查询 DTO、Normalizer、Service、Mapper 及测试 | 使用固定数据集验证概览、日/周/月趋势及两个维度汇总 | `fix(report): standardize report query contracts` |
| B4 | 建立业务查询性能基线 | 性能数据脚本、核心查询 SQL、执行计划和基线记录 | 在固定环境与数据量下保存列表、筛选及报表的原始结果 | `test(perf): establish business query baselines` |
| B5 | 优化列表与聚合查询 | `advertiser/delivery/report` Mapper、必要的新 Flyway 迁移及持久化测试 | 使用 B4 的相同条件复测，并执行结果正确性回归 | `perf(report): optimize business queries and indexes` |
| B6 | 对齐业务模块接口文档与日志 | 三个模块的 Controller 注解、必要业务日志和 OpenAPI 测试 | 核对 Swagger 参数、权限、状态码、错误响应及非敏感日志 | `docs(api): align advertiser delivery report contracts` |
| B7 | 板块 B 总回归与验收记录 | 三个模块的专项测试、`docs/sprint3-B-business-optimization.md` | 运行模块测试和全量测试，记录规则、性能对比、结果及限制 | `test(sprint3): record module B acceptance` |

建议执行顺序为 B1 → B2 → B3 → B4 → B5 → B6 → B7。先确认三个模块的功能正确性，再建立性能基线和实施优化，最后统一 Swagger、日志和验收文档。

#### 各提交的边界

- B1 只处理广告主和分类，不混入投放或报表修改。
- B2 只处理投放数据事实；不隐式修改账户余额或历史资金流水。
- B3 先固定查询参数和统计口径，不在同一提交中进行索引调优。
- B4 只建立可复现基线，不提前宣称优化效果。
- B5 只提交有 B4 证据支持的优化；若需数据库变更，必须新增 Flyway 迁移。
- B6 只对齐 B 板块接口文档与业务日志，不修改 A 板块公共机制。
- 未发现问题的小任务不创建无意义代码变更，其检查结论统一归档到 B7。

#### 完成标准

- 广告主、投放和报表的非法输入均能被明确拒绝。
- 固定数据集下的接口结果与人工计算或验收 SQL 一致。
- 核心查询具有可复现的优化前后数据或执行计划结论。
- 所有性能修改保持查询结果和业务规则不变，新增索引有明确访问模式依据。
- Swagger 可以完整演示广告主、投放录入、筛选和四类报表链路。

### 4.3 板块 C：认证、用户与资金交易模块

> 对应模块：`auth`、`user`、`account`、`payment`

#### 目标

围绕“用户登录与授权”和“充值 → 入账 → 消费 → 流水”两条高风险链路，完善安全校验、日志、事务、幂等和并发一致性。

#### 主要任务

- 复查注册、登录、BCrypt、JWT、账号状态和认证限流行为。
- 复查 `ADMIN`、`OPERATOR` 的接口权限，以及最后一个启用管理员保护。
- 统一认证失败、权限不足、账号禁用、限流和参数错误的响应语义。
- 复查账户唯一性、金额精度、余额非负、业务流水号唯一和流水不可变规则。
- 复查消费的广告主/投放归属、原子扣款、余额不足、请求幂等和事务回滚。
- 复查充值订单状态机、HMAC 验签、时间窗口、事件幂等和订单终态保护。
- 检查消费与支付回调的锁顺序、事务长度、重复查询和并发竞争。
- 为登录失败、用户状态变更、消费、充值和回调增加必要的 `WARN`/`INFO` 日志。
- 确保日志和异常响应不记录密码、完整 JWT、回调密钥、原始签名或敏感请求体。
- 运行并补充重复消费、重复回调、并发扣款、并发回调和异常回滚测试。

#### 核心检查对象

| 模块 | 关键风险 | 必须保留的保护 |
| --- | --- | --- |
| `auth` | 暴力登录、无效 Token、敏感信息泄露 | BCrypt、JWT 校验、限流和安全日志 |
| `user` | 越权操作、系统失去管理员 | RBAC、状态校验和最后管理员保护 |
| `account` | 负余额、重复扣款、流水不一致 | 原子更新、业务号幂等和同事务写流水 |
| `payment` | 伪造回调、重复入账、状态回退 | HMAC、事件幂等、订单锁和终态保护 |

#### 可独立提交的小任务

| 编号 | 小任务 | 主要文件范围 | 单独验收方式 | 建议 Commit |
| --- | --- | --- | --- | --- |
| C1 | 完善注册、登录与 JWT 安全 | `auth` 的 Controller、Service、Token、Security、DTO 及测试 | 验证 BCrypt、JWT 有效/过期/篡改、账号状态和限流 | `fix(auth): harden authentication boundaries` |
| C2 | 完善用户状态与 RBAC | `user`、相关 `SecurityConfig` 规则及测试 | 验证角色权限、待审批/禁用账号、最后启用管理员和并发保护 | `fix(user): enforce account and admin invariants` |
| C3 | 统一账户余额与流水查询 | `account` 查询 Controller、DTO、Service、Mapper 及测试 | 验证账户唯一性、分页筛选、流水顺序、金额精度和权限 | `fix(account): standardize balance and ledger queries` |
| C4 | 强化消费事务与幂等 | 消费 Service、Mapper、错误码及并发/持久化测试 | 验证原子扣款、余额不足、业务号幂等、归属关系和异常回滚 | `fix(account): harden idempotent consumption` |
| C5 | 完善充值订单状态机 | 订单 Controller、Service、状态机、Mapper 及测试 | 验证创建、查询、合法迁移、终态保护和金额规则 | `fix(payment): enforce recharge order lifecycle` |
| C6 | 强化支付回调安全与入账一致性 | 回调验签、模拟入口、回调 Service、Mapper、日志及并发测试 | 验证签名、时间窗口、金额篡改、重复/并发回调和单次入账 | `fix(payment): harden callback idempotency` |
| C7 | 板块 C 总回归与验收记录 | 四个模块专项测试、`docs/sprint3-C-security-transaction-acceptance.md` | 运行安全、权限、交易及并发测试，记录结果与剩余风险 | `test(sprint3): record module C acceptance` |

建议执行顺序为 C1 → C2 → C3 → C4 → C5 → C6 → C7。认证和用户权限先稳定，随后验证账户查询与消费，再处理订单和回调，最后执行完整交易链路回归。

#### 各提交的边界

- C1 负责身份认证，不同时调整业务资源的角色权限。
- C2 负责用户状态和授权规则，不修改账户或支付逻辑。
- C3 只处理账户及流水的读取契约；余额写入和消费事务放在 C4。
- C4 只处理消费链路，不复用消费接口实现充值。
- C5 只固定订单创建、查询和状态机；成功入账与回调幂等放在 C6。
- C6 必须把订单更新、余额增加、充值流水和回调审计作为一个事务验证。
- 涉及安全或资金的修改必须在对应提交中附带失败、重复和并发测试。

#### 完成标准

- 未认证、无权限、无效状态和限流场景均返回稳定错误码。
- 一笔消费只扣款一次，一笔成功充值只入账一次。
- 并发请求不会造成负余额、重复流水或订单状态回退。
- 订单、账户余额和资金流水在成功及失败路径中保持一致。
- 高风险链路有足够的安全日志和自动化测试，且不存在敏感信息泄露。

## 10. 主要风险与处理方式

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 最后一周继续增加业务功能 | 工程化和总结无法按时完成 | 冻结业务范围，只处理缺陷、规范、优化、测试和文档 |
| 为统一结构进行大范围重构 | 引入回归且难以定位 | 小步提交，每次改动配套测试，优先修复真实不一致 |
| 没有基线就宣称性能提升 | 优化结论无法证明 | 固定环境、数据和请求，保存前后结果及执行计划 |
| 盲目增加索引或缓存 | 写入变慢或产生一致性问题 | 以访问模式和测量结果决定，缓存保持可选 |
| 日志过多或记录敏感信息 | 噪声、性能和安全风险 | 明确级别、集中记录、脱敏检查，不记录密码和密钥 |
| 文档与代码再次不同步 | 项目无法顺利交接 | 按文档在干净环境实际执行一次部署、测试和 Demo |
| 总结报告只有概念没有证据 | 难以体现项目成果 | 每个难点和优化都关联代码、测试、SQL 或日志证据 |

## 11. 最终交付结论标准

Sprint 3 结束时，项目应当达到以下状态：业务范围冻结，现有功能全部可运行；统一响应、校验、异常和日志规范覆盖完整；核心接口经过有证据的性能复查；代码与文档完成整理；全量测试和 Demo 可重复执行；最终总结报告能够清楚回答“系统做了什么、为什么这样设计、解决了哪些难点、如何证明正确、还能如何扩展”。
