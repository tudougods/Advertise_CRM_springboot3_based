# Advertiser CRM Sprint 3 开发计划

> Sprint 主题：工程化完善与项目总结
>
> 计划周期：第 4 周（最后一周）
>
> 状态：A–D 板块已完成，最终验收通过（2026-09-04）
>
> 本计划严格对应导师给出的四项工作内容，不增加新的业务功能或独立工作板块。

## 1. Sprint 目标

本周在 Sprint 1、Sprint 2 已完成功能的基础上进行工程化收尾，重点不是继续增加功能，而是规范现有接口、优化系统、整理项目并完成总结复盘。

Sprint 3 分为四个板块：

| 板块 | 导师要求 | 小任务数 |
| --- | --- | --- |
| A | 工程规范完善 | 3 |
| B | 系统优化 | 3 |
| C | 项目整理 | 2 |
| D | 项目总结与复盘 | 3 |

本周最终产出为《后端系统总结与优化报告》，内容包括：

- 系统架构总结。
- 核心技术难点分析。
- 优化点说明。
- 项目亮点提炼。
- 未来扩展方向。

## 2. Commit 原则

- 每个小任务完成并通过对应测试后再 Commit。
- 同一小任务的代码、测试和直接相关说明放在同一个 Commit 中。
- Review 后如果现有实现已经满足要求，只在最终报告中记录检查结论，不创建无意义的代码提交。
- 不为了增加 Commit 数量拆分测试、注释或文档。
- 一个 Commit 只处理一个小任务，能够独立说明、验证和回滚。

## 3. 板块 A：工程规范完善

### A1. 完善统一返回结构与错误码体系

#### 工作内容

- 检查所有 Controller 是否统一使用 `ApiResponse<T>`。
- 检查分页接口是否统一使用 `PageResponse<T>`。
- 统一成功、失败和无数据响应的字段结构。
- 检查公共错误码和各业务模块错误码的命名。
- 确保一个错误码只表达一种明确含义。
- 检查错误码与 HTTP 状态码的对应关系。
- 补充统一响应和错误码测试。

#### 完成标准

- 所有接口使用一致的响应结构。
- 相同类型的错误返回一致的 HTTP 状态。
- 错误码具有清晰的模块前缀，不重复、不混用。
- Swagger 展示的响应与实际接口一致。
- 对应自动化测试通过。

#### Commit

```text
fix(common): standardize response and error codes
```

### A2. 增强参数校验机制，防止非法输入

#### 工作内容

- 检查请求 DTO 的必填、长度、格式、范围和枚举校验。
- 检查路径参数和查询参数中的 ID、分页、日期及排序字段。
- 检查开始日期与结束日期、展示与点击、点击与转化等跨字段规则。
- 检查金额精度、非负数和最大值限制。
- 确保非法输入在进入核心业务逻辑前被拒绝。
- 补充空值、边界值、非法格式和跨字段错误测试。

#### 完成标准

- 非法输入能够稳定返回 400 响应。
- 校验错误能够指出具体字段或业务规则。
- Controller 参数校验和 Service 业务校验职责清楚。
- 关键数据库约束仍作为最后一道保护。
- 对应自动化测试通过。

#### Commit

```text
fix(validation): strengthen request validation
```

### A3. 实现并完善全局异常处理机制

#### 工作内容

- 检查业务异常是否统一由全局异常处理器转换。
- 处理参数校验失败、类型转换失败和非法 JSON。
- 处理资源不存在、数据冲突和权限相关异常。
- 为未知异常保留统一兜底响应。
- 保证客户端响应不暴露堆栈、SQL、文件路径或敏感信息。
- 避免同一异常在不同层重复记录。
- 补充各种异常场景的 MockMvc 测试。

#### 完成标准

- 已知异常返回明确错误码和正确 HTTP 状态。
- 未知异常返回统一安全提示。
- 所有异常响应保持统一结构。
- 服务端保留必要的错误定位信息，客户端不看到内部细节。
- 对应自动化测试通过。

#### Commit

```text
fix(common): complete global exception handling
```

## 4. 板块 B：系统优化

### B1. 优化核心接口性能

#### 工作内容

- 确定当前系统的核心高频接口。
- 检查列表查询是否使用数据库物理分页。
- 检查报表查询的日期范围、聚合 SQL、JOIN 和排序。
- 排查重复查询、无界查询、N+1 查询和无用字段返回。
- 使用固定数据和相同环境记录优化前性能。
- 使用 `EXPLAIN ANALYZE` 检查核心 SQL。
- 根据实际证据优化 SQL 或索引。
- 使用相同条件记录优化后结果。

#### 完成标准

- 核心接口具有可复现的优化前后对比。
- 性能优化不改变接口返回结果和业务规则。
- 新增或调整的索引具有明确查询依据。
- 没有测量依据时不盲目增加缓存或索引。
- 优化后的相关测试通过。

#### Commit

```text
perf(api): optimize core interface performance
```

### B2. 完善日志体系，区分不同日志级别

#### 工作内容

- 检查请求日志是否包含 Request ID、请求方法、路径、状态和耗时。
- 统一 `ERROR`、`WARN`、`INFO`、`DEBUG` 的使用场景。
- 为关键业务状态变化补充必要日志。
- 为可预期的业务失败使用合适的日志级别。
- 未知系统异常只保留一次完整错误日志。
- 不记录密码、完整 JWT、密钥、原始签名等敏感信息。
- 验证成功、业务失败和系统异常场景的日志行为。

#### 日志级别

| 级别 | 使用场景 |
| --- | --- |
| `ERROR` | 未知系统异常、依赖故障和必须立即处理的错误 |
| `WARN` | 已处理但需要关注的业务异常或风险事件 |
| `INFO` | 请求完成和关键业务状态变化 |
| `DEBUG` | 本地排查所需的非敏感内部信息 |

#### 完成标准

- 不同类型事件使用正确的日志级别。
- 可以通过 Request ID 定位一次完整请求。
- 日志能够支持问题排查，且不过度重复。
- 日志中不包含敏感信息。
- 对应测试或检查记录完成。

#### Commit

```text
refactor(logging): complete application log levels
```

### B3. 提升系统可读性与可维护性

#### 工作内容

- 检查类、方法、DTO、错误码和数据库对象命名。
- 简化过长方法和职责不清的代码。
- 删除重复逻辑、无效注释和未使用代码。
- 保持 Controller、Service、Mapper 的职责边界。
- 检查公共逻辑是否被合理复用。
- 检查事务边界和跨模块依赖是否清晰。
- 对重构影响的功能执行回归测试。

#### 完成标准

- 代码命名清晰且风格一致。
- Controller 不承载核心业务逻辑。
- Service 不直接拼接 HTTP 响应。
- 不存在明显重复逻辑和过期代码。
- 重构前后业务行为保持一致。
- 受影响测试全部通过。

#### Commit

```text
refactor(core): improve readability and maintainability
```

## 5. 板块 C：项目整理

### C1. 整理代码结构，确保模块清晰

#### 工作内容

- 检查现有业务模块的目录结构。
- 保持模块内部 `controller/service/mapper/entity/dto/exception` 分层一致。
- 检查公共能力是否位于 `common` 或 `config`。
- 检查业务代码是否放入正确模块。
- 删除空目录、临时文件和无用生成物。
- 更新项目模块结构说明。
- 运行编译和相关回归测试。

#### 完成标准

- 项目能够按业务模块快速定位代码。
- 各模块分层结构清晰且职责明确。
- 不存在明显放错位置的业务代码。
- 项目中没有应删除的临时文件。
- 整理后项目能够正常编译并通过相关测试。

#### Commit

```text
refactor(project): organize module structure
```

### C2. 编写项目说明文档

#### 工作内容

- 说明项目背景和主要业务功能。
- 说明技术栈和模块结构。
- 说明运行所需的环境和配置。
- 编写项目部署方式。
- 编写项目运行方式。
- 说明数据库初始化和应用访问入口。
- 按文档实际验证相关命令。

#### 完成标准

- README 能够说明项目用途、技术栈和模块结构。
- 文档包含导师要求的部署与运行方式。
- 配置说明不包含真实密码或密钥。
- 文档中的命令、路径和访问地址与项目一致。
- 其他开发者能够根据文档运行项目。

#### Commit

```text
docs(readme): complete project setup and usage guide
```
